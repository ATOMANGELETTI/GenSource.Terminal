1. notify (already in tree) — highest priority
Wire a watcher on the SCM root (debounce ~200–500ms) → emit a Tauri event → frontend calls git_status again.

That is the VS Code-like “files changed → panel updates” behavior. No new crate required.

Optional polish: ignore .git/ noise, debounce bursts from builds, pause while a commit/checkout is in flight.

2. Stay on gix and turn on more features
Don’t add a second git stack unless you hit a hard wall. For closer VS Code parity, extend gix rather than replacing it:

Diff preview (click a change → see hunks)
gix blob/tree APIs + a diff crate (below)
Stash list / stash / pop / apply
Build on gix refs + tree ops (more work; no magic crate)
Push / pull / fetch
Enable gix network features (e.g. blocking-network-client / related) — omitted on purpose in v1
Credentials
gix-credentials / credential helpers (Windows Credential Manager, etc.)
Merge / conflict content
Read conflicted blobs via gix; UI for 2/3-way still app-side
Ignore / .gitignore
You already enable excludes / attributes

3. Diff UI helpers (small, useful)
similar or imara-diff — turn “old blob vs new blob” into line hunks for a side-by-side or unified diff view (VS Code’s diff editor lite).
gix can supply the before/after bytes; these crates format the presentation.
4. git2 (libgit2) — only if needed
Mature porcelain for stage/diff/merge/remotes, but it’s a C dependency, larger binary, and overlaps gix. Prefer it only if a specific operation is painful in gix (e.g. some merge/rebase edge cases). Mixing both long-term is usually worse than deepening gix.
